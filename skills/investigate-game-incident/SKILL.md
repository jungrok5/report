# 게임 장애 근거 보고서

관측한 현상과 조치를 공통 시간축으로 먼저 보여주고, 바로 아래에 원인 또는 가장 유력한 후보를 요약하라. 원인 그래프, 조사 기록, 검증 근거를 통해 독자가 결론을 재확인할 수 있게 작성하라.

## 시작하기

1. 제공된 자료와 접근 가능한 도구를 먼저 확인하라. 이미 승인된 읽기 범위에서 조사하라.
2. 사건 범위·시간대·영향 월드·관측 공백을 확인하라. 누락된 핵심 정보가 있을 때만 질문하고 나머지는 진행하라.
3. 자료가 불충분하면 예비 보고서를 작성하라. 수치, 조회 결과, 원본 URL, 실행한 검증을 만들어내지 말라. 샘플 데이터는 `meta.synthetic=true`로 표시하라.
4. [분석 절차](references/investigation.md)를 읽어 후보를 좁히고, [데이터 규약](references/report-contract.md)에 맞춰 `incident.json`을 작성하라.
5. HTML 산출물이 필요하면 다음 명령을 실행하라. Python 3.10+ 표준 라이브러리만 필요하다.

```bash
python scripts/render_report.py incident.json --out report.html --markdown-out report.md
```

상대 경로를 이 스킬 디렉터리 기준으로 해석하라. 제공된 자료를 분석하는 대신 예제를 결과로 제출하지 말라. 시안을 요청받았을 때만 `assets/example-restart.json`을 사용하라.

## 실데이터 조회·반복 조사

연결·자동 조사 요청이면 [조회·조사 엔진](references/engine.md)을 읽고 `scripts/investigate.py`를 사용하라. 사람이 정한 읽기 전용 카탈로그로 Prometheus/Loki를 조회하고 DB·클라이언트·dump JSON을 import한다. 주소가 없으면 예비 보고서와 설정 초안을 만들고 연결에 필요한 정보를 묻는다. 가상 replay를 운영 조회나 실제 Holmes 모델 실행이라고 주장하지 말라.

Chat Completions 호환 자체 planner(`--planner compatible`)도 같은 근거·카탈로그 검증 루프를 사용한다. 실제 모델을 호출하지 않은 모의 검증과 실제 운영 실행을 구분하라.

Holmes 모드는 서버 도구를 끈 별도 planner 인스턴스와 데이터 전송이 승인된 범위에서 실행하라. 후보는 검토 전 verified로 승격하지 않는다. `state.json`의 실패·중단 이유, 부분 결과와 마스킹 보존본 해시를 확인하라. 운영 변경·자동 복구·메시지 전송은 수행하지 않는다.

## 화면·버전·검토

React Flow 화면, 근거 저장 구조, 전달용 버전·검토를 요청받으면 [보고서 워크벤치](references/workbench.md)를 읽어라. 기존 내용·구성을 유지한 `incident.json`을 생성하고 보고서 페이지에서 열 수 있게 한다. 제공 자료와 exact evidence bytes를 `scripts/report_store.py`로 저장하고 revision·작성자·검토 의견·내용 해시를 포함한 JSON을 export하라. 검토 초안은 해당 report ID·revision·해시가 일치할 때만 반영한다. 새 버전은 검토 대기이며 이전 검토를 자동 승계하지 않는다.

검토 완료를 원인 검증됨으로 해석하지 말라. 검토자 이름은 CLI 입력 기록이며 인증된 신원이 아니다. 과거 실제 장애 자료가 없으면 가상 사례를 명시하며 실제 3건 검증을 완료했다고 주장하지 말라.

## 현상부터 보여주기

- 제목·범위 아래, 원인 요약보다 위에 장애 전후 시간축을 배치하라. 정상 구간, 악화, 조치, 서비스 회복을 포함하라.
- 사건·알림·조치와 수치 그래프를 하나의 절대 시간축에 겹쳐 표시하라. 지표는 색과 선 모양으로 구분하라. 단위가 다른 지표는 0을 포함한 각 관측 범위로 표시 높이를 정규화하고, 축과 범례에 상대 높이와 실제 범위를 명시하라. 서로 다른 지표의 크기를 비교하는 축처럼 표현하지 말라.
- 마우스·터치·키보드 탐색에서 같은 시각의 모든 지표를 함께 보여주어라. 툴팁에 실제 값, 단위, 실제 표본 시각, 집계 의미 또는 description을 표시하라. 가까운 원본 표본을 사용할 때는 보간값이나 해당 시각의 정확한 관측처럼 표현하지 말라.
- 종료, 알림, 동접 감소, 재부팅, 로딩 시작, DB 부하 피크, 접속 회복을 원본 발생 시각에 표시하라. 수신·조회 시각과 조사 시각은 별도 기록하라.
- 사건 선택 시 모든 지표에 같은 시각선을 표시하고 당시 값과 근거를 보여주어라. 클릭·키보드로 확인할 수 있는 사건 목록을 제공하라.
- 실제 알림 규칙이 제공된 경우에만 임계값을 표시하라. 공백은 끊어진 선으로 표시하고 0으로 채우지 말라. p99의 평균을 전체 p99라고 쓰지 말라.
- 재부팅·DB 부하 증가의 선후 관계만으로 원인을 단정하지 말라. `조치 직후`, `동시 관측`과 검증한 인과관계를 구분하라.

## 결론과 근거

- 요약을 `직접 원인/현재 후보 → 장애 메커니즘 → 유저 영향 → 복구 결과`로 작성하라. 증거 상태와 남은 질문도 짧게 표시하라.
- 원인 불명 시 `미확인`, 증거가 지지하되 대안이 남으면 `유력`, 직접 관계·개입·재현 등으로 검증했다면 `검증됨`으로 표시하라. 근거 없는 확률 점수를 만들지 말라.
- 직접 원인, 촉발 조건, 영향 확대 요인, 관측된 결과, 완화 조치를 구분하라. 하나의 원인으로 강제하지 말라.
- 노드와 화살표 모두에 근거 ID를 연결하라. 상관관계만 있는 연결은 `유력` 또는 `미확인`으로 표시하라.
- 조사 과정에 질문·가설·예측·조회·관측·판정·다음 질문을 기록하라. 배제한 후보와 모순 근거도 보존하라. AI 내부 사고 대신 재현 가능한 조회와 판단을 기록하라.
- 조치는 이미 수행된 기록을 분석하라. 보고서 작성 권한을 운영 변경·자동 복구 권한으로 해석하지 말라.

## 증거 보존

- 출처, 발생 범위, 조회 시각, 데이터소스, 쿼리, 변수, 집계 방법, 표본, 원본 링크, 보존본 위치, 한계를 기록하라.
- Grafana 링크는 절대 `from`/`to`와 데이터소스·변수를 저장하라. `now-1h` 링크만 남기지 말라. 링크를 지어내지 말라.
- 당시 결과도 보존하라. Snapshot이 쿼리까지 보존한다고 가정하지 말라.
- 개인정보·토큰·비밀번호를 포함하지 말라. 필요한 표본만 익명화하고 출처 열람 권한을 유지하라.

## 완료 점검

1. `python scripts/validate_report.py incident.json`을 실행하고 오류를 수정하라. 검증기는 형식과 참조를 확인하며 원인 진위를 증명하지 않는다.
2. 제목 → 현상 시간축 → 원인 요약 → 인과관계 → 조사 과정 → 조치·미확인 순서를 확인하라.
3. 원인 표현이 근거 상태보다 강하지 않은지 확인하라. 수집 장애, 시계 오차, 샘플링, 누락을 검토하라.
4. 사용자 영향과 매출·보상·데이터 정합성을 관측 범위 안에서만 기술하라.
5. 가능하면 브라우저에서 사건·시각선 연동, 노드·근거 선택, 링크, 320px·데스크톱·인쇄를 확인하라. 실행하지 못했다면 검증 범위를 정확히 알리라.
6. 전달할 팀·담당자·기한·완료 기준을 기록하라. 요청받지 않은 메시지 전송은 하지 말라.
